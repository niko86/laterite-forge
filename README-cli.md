# laterite-ags4-forge

Evolutionary AGS4 dual-validation dogfood generator. It **generates**
AGS4 files and runs each through the in-process Rust validator and
(when available) the official `python-ags4`, classifying every result
with the shared `laterite-ags4-parity` model (the same `classify`/`reconcile`
+ O-2/O-3/O-26/O-30/O-34 arms `laterite-ags4-corpus-qa` uses). A declarative
strategy file drives the loop; this binary is the deterministic
mutate/validate/report muscle and embeds **no LLM**.

> Status: **complete (P0–P5)** — `check`, `gen`, `run` (the
> evolutionary loop), `minimize` (ddmin), `strategy
> new|validate|explain`, `confidence show|reset|export`, `seed
> vendor`; the persistent adaptive parity-confidence ledger; first
> finding ratified ([[strat-forge-rule10a-relational]] retired the
> Rule-10a parity blind spot; the O-35/O-3-narrow cascade was
> reproduced, not re-opened). See `docs/laterite-ags4-forge.md` in this repo
> and `ags-wiki/concepts/evolutionary-dogfooding.md` in niko86/laterite.

## Commands

```
laterite-ags4-forge check <path>... [--no-oracle] [--timeout S] [--oracle-project DIR]
laterite-ags4-forge gen [--scaffold minimal|loca-samp] [--inject TOK]... \
               [--validate] [--no-oracle] [--oracle-project DIR] [--out-dir D]
laterite-ags4-forge gen --site PRESET [--seed N] [--grid bng --origin E,N] \
               [--inject TOK]... [--validate] [--out-dir D]
laterite-ags4-forge scale --site PRESET --size SIZE [--seed N] \
               [--grid bng --origin E,N] [--inject TOK --density P] [--out F]
```

- **check** — dual-validate existing files; print each side's rule set,
  its **per-rule finding counts**, and the parity verdict. The verdict
  stays presence-only by design (see `ags-wiki/concepts/parity-model.md` in
  niko86/laterite);
  the counts sit beside it because one side saying a rule nine times and
  the other saying it once is the same verdict and a very different file.
  A **directory** is walked recursively for `.ags` files (extension match
  is case-insensitive) and several paths may be given at once — one run,
  one report, one python process per file rather than per invocation. The
  report says how many non-`.ags` entries it walked past.

  One file named directly emits the single-file document (schema 2); a
  directory or more than one path emits the sweep document — a verdict
  tally, the scanned/skipped counts, and one entry per file (dropped by
  `--compact`).
- **gen** — synthesize a spec-valid base (`loca-samp` adds a real
  LOCA→SAMP + ABBR relational scaffold, which is what makes the
  Rule 10a/10c/16 parity blind spots single-rule-injectable), apply
  each `--inject` (`none|rule10a|rule10c|rule8|rule5|rule19|rule13`),
  write the `.ags` candidates under `<out>/runs/<id>/`, and
  (`--validate`) dual-validate each.

## Site model

`gen --site` and `scale --site` generate from a **preset** instead of a
scaffold: a description of believable synthetic ground (units with smooth
surfaces across the site, a sampling schedule per unit, index properties,
strength and groundwater) from which forge builds holes, strata, samples and
the preset's test suite. `--site` and `--scaffold` are mutually exclusive.

- **Presets.** Two presets ship, each with LNMC, LLPL, LDEN, TRIG/TRIT,
  ISPT and WSTG/WSTD results:
  - `--site london-basin`: Made Ground over River Terrace Deposits over
    weathered and unweathered London Clay.
  - `--site tyneside-till`: weathered, red and grey glacial till of NE
    England, with a water-bearing glaciofluvial sand and gravel lens in the
    grey till.

  `--site path/to/preset.toml` loads your own. Every range in a preset carries
  a cited `basis`; the loader refuses one without, and refuses an unknown key,
  naming the field (exit 5). `data/presets/london-basin.toml` is the worked
  example, and `docs/research/london-basin-sources.md` and
  `docs/research/tyneside-till-sources.md` record where each preset's values
  come from.
- **SYNTHETIC marker.** Every `--site` file says in `PROJ_MEMO` that it is
  synthetic, naming the preset and its version (`SYNTHETIC: generated by
  laterite-ags4-forge from site preset london-basin v8. Not real ground
  data.`). It is not real ground data and must not be presented as such.
- **Grids.** Holes sit on a local grid (`LOCA_LOCX`, `LOCA_LOCY`) by
  default. `--grid bng --origin E,N` adds British National Grid columns
  (`LOCA_NATE`, `LOCA_NATN`, `LOCA_GREF`) offset from an origin you choose
  and are responsible for. No shipped preset carries a real origin, because
  a believable log on real land can be mistaken for real site data.
- **Determinism and prefix stability.** The same preset version and seed give
  the same bytes. `gen --site` draws 3-7 holes from the seed. Every draw is
  keyed by seed, hole, unit and test, so hole k is the same whatever the hole
  count: a smaller `scale --site` file is a prefix of a larger one, group by
  group. `--inject` and `--combine` work on a site base as on a scaffold.
- **Versioning.** From london-basin v3, any change to what a shipped preset
  generates bumps its `version` (which the marker records), and consumers are
  told and re-baseline. Old versions are not kept, so pin the forge release
  if you need the old bytes. london-basin v4, which adds Made Ground at the
  top of every hole, is the first such bump. tyneside-till ships at v1 under
  the same promise. london-basin
  v5 and tyneside-till v2 add SPT refusals: the ISPT rows carry `ISPT_MAIN`,
  `ISPT_NPEN` and `ISPT_REP`, and a test that reaches 50 blows before the full
  300 mm main drive is written as N 50 (not extrapolated), MAIN 50, NPEN 150
  plus the penetration reached and REP "50/<mm>". Every N above 50 in earlier
  versions is now 50. london-basin v6 and tyneside-till v3 add a **cover
  layer**: a preset's `[cover]` block gives each hole surfacing (`MADE
  GROUND: Tarmacadam.`, `Concrete.` or `Paving slabs.`), topsoil (`Dark brown
  slightly gravelly sandy TOPSOIL with rootlets.`) or nothing. The cover takes
  its thickness off the top of the first stratum, so the file gains one GEOL
  row and the first stratum's top moves down; every other boundary, sample,
  test and strike is where it was, and nothing is sampled or tested in the
  cover. A sample that would start in the cover moves to its base or is
  dropped, leaving a gap in `SAMP_REF`.
  tyneside-till v4 adds **multi-stage UU triaxial** tests: about
  54% of its TRIG tests are `TRIG_TYPE` `UUM`, each with three TRIT rows
  (`TRIT_TESN` 1 to 3, cell pressure at 1, 2 and 4 times the single-stage
  value, `TRIT_CU` rising from stage to stage, and the specimen's density and
  moisture content repeated). Single-stage tests are as v3 wrote them;
  london-basin is unchanged.
  tyneside-till v5 adds **effective-stress triaxial** results: about as many
  `TREG` sets as `TRIG` tests, each a `TREG_TYPE` of `CUM`, `CDM`, `CU` or `CD`
  with three `TRET` rows (`TRET_TESN` 1 to 3: three stages on one specimen
  for `CUM` and `CDM`, three specimens for `CU` and `CD`). The effective
  confining stress is 10 kPa per metre of depth for stage 1 and twice and four
  times that for stages 2 and 3, on a 300 kPa back pressure (`TRET_PWPI`), so
  `TRET_CELL` is the two added and `TRET_CONP` the effective stress. The
  deviator stress `TRET_DEVF` is on the Mohr-Coulomb envelope of the till's
  c' and phi'; in `CU` and `CUM` the pore pressure `TRET_PWPF` rises by
  Skempton's A_f times it, and in `CD` and `CDM` it does not. `TREG_COH` and
  `TREG_PHI` are the line through the set's three failure points. Every other
  group is as v4 wrote it; london-basin is unchanged.
  london-basin v7 and tyneside-till v6 add **hole construction** for holes
  with no installation. `HDPH` has two rows per hole, an inspection pit
  (`IP`, 0 to 1.2 m) then `CP` to final depth, and `LOCA_TYPE` is the phases
  joined, `IP+CP`. `CDIA` records the casing of every hole, in one string or two (a larger
  diameter to part depth, a smaller below, never the other way round), ending
  above final depth by a gap fitted to the crawls; the casing passes the first
  water strike in 82% (tyneside-till) or 92% (london-basin) of holes. Every
  `WSTG` row gains `WSTG_CAS`, the casing depth at the strike, never deeper
  than the strike or the final casing. Some sites (about 7 in 10 for
  tyneside-till, 1 in 2 for london-basin) also carry `BKFL`: arisings,
  bentonite, or arisings over bentonite, from 0 to final depth, as legend
  codes 905 and 903. `ABBR` lists `IP` and `CP` separately. Every other group
  is as v6 and v5 wrote it.
  london-basin v8 and tyneside-till v7 add **installations**. A site draws
  once whether it installs at all (about 1 in 2 for tyneside-till, 1 in 6 for
  london-basin), then a share of its holes (0.43 to 1.0), and each hole draws
  against it. An installed hole has one installation, `PIPE_REF` 1: a 50 mm
  standpipe (`PLAIN` from the surface to the top of the response zone, then
  `SLOTTED` through it) or a 19 mm piezometer (`PLAIN`, then a 0.3 m tip
  written as `SLOTTED`, because `PIPE_TYPE` has only those two values). The
  zone starts at the first strike plus a drawn offset, or at a drawn depth when
  there is no strike, and is placed by depth alone. An installed hole also
  carries its own `BKFL`, even on a site whose other holes have none: concrete
  cap (906), bentonite (903), a gravel (902) or sand (901) filter from 0.5 m
  above the slotted section to 0.5 m below it, bentonite to final depth. There
  is no `MONG`. Every other group is as v7 and v6 wrote it.
  tyneside-till v8 adds **water strikes in the tills**. Each till (weathered,
  red, grey) strikes water along its depth at a rate per metre penetrated,
  fitted so that 7.3%, 14.9% and 17.7% of the holes through each strike in it
  (the NE crawl's 7.3%, 15.0% and 17.7%); the strike falls evenly through the
  stratum. A v8 hole still records one strike: the shallowest of a lens-top
  strike and a till strike, with a water-table strike counted only when
  neither occurs. The water always rises by a drawn amount, whatever the
  depth of the water table, but not above ground level (12% of strikes draw no
  rise). In v8 the lens share is raised to 0.44 so holes with the lens strike in
  it at the crawl's 36% (v9 returns it to 0.36). Holes with any strike rise from about 7% to about 35%, and
  `WSTG`, `WSTD`, `WSTG_CAS`, the installation zone and `BKFL` follow the
  strikes. london-basin is unchanged.
  tyneside-till v9 adds **several strikes per hole**. A hole records every
  strike its sources give, shallowest first, up to four and never closer than
  0.5 m: each water-bearing lens that yields (at its top), each till's strikes
  (the rate now runs on past the first), and the water table in a coarse
  stratum with no strike of its own. A shallower till strike no longer takes
  precedence over the lens, so the lens share goes back to 0.36, and the till
  rates are re-fitted to the same 7.3%, 15.0% and 17.7%. Each strike has its
  own `WSTD` rows. A later strike's `WSTG_CAS` is at least the strike above it,
  or that strike's seal, and the final casing passes every strike but the last.
  `WSTG` gains `WSTG_SEAL` (48% of earlier strikes, 25% of last strikes, a
  drawn gap below the strike). The installation zone in a hole with several
  strikes follows the first strike or the deepest. About 19% of struck holes
  have two strikes or more (the crawl's 24%); the file has no made-ground,
  laminated-clay, alluvium or rock strikes, so it falls short of the crawl's
  multi-strike share. london-basin is unchanged.

## Finding python-ags4

The oracle runs as `uv run python tools/py_ags4_check_json.py` inside a uv
project whose `pyproject.toml` pins python-ags4. By default that is the
checkout the binary was built from, which is right for `cargo run`. A
downloaded release was built elsewhere, so point it at a laterite-forge
checkout with `--oracle-project DIR` (or `$AGS4_FORGE_ORACLE_PROJECT`) and run
`uv sync` there. When no oracle is found, forge falls back to Rust-only
verdicts (`"oracle": false`), and stderr says why and how to supply one.
The verdicts are written for python-ags4 1.2.0, the version the checkout
pins; if the project reports any other version, forge still uses it and warns
on stderr.

## Conventions (shared CLI contract)

Results to **stdout** in the resolved mode (`--output table|json|ndjson`,
`--json`; ndjson auto when piped); progress/hints to **stderr**;
`--quiet`, `--no-color`, `--no-input`; `--dry-run` mutates nothing;
`--compact` is the token-lean agent view (drops the per-candidate
array). `--readme` prints this guide.

## Exit codes

```
0  success / no parity action (clean or documented divergence)
1  parity action — a real Rust↔python divergence to triage
3  I/O — file not found / out-dir unwritable
5  bad args (unknown --scaffold / --inject token)
```

## Guarantees

- Generated files are written only under the run dir; a `--out-dir`
  resolving inside `laterite-ags4-validator/tests/fixtures/` is refused
  (that tree is asserted hard-error-free). Confirmed reproducers are
  evidence for a niko86/laterite issue, never `tests/fixtures/` files.
- The synthetic base is clean **by construction** from the validator's
  bundled v4.2 standard dictionary; a test asserts `RustResult::Clean`
  on the un-injected base, so a generator bug is a test failure, never
  a reported "finding".
